# ADR-007: 材料データを持つ（まとめ買い献立のため）

## Status
Accepted（ADR-003 を一部変更）

## Date
2026-07-31

## Context

「買い物1回で3〜7日分の献立を組みたい」という要求が出た。これを成立させるには、

- にんじんやじゃがいもは**1本ずつ売っていない**（袋・パック単位でしか買えない）
- 肉は**大容量パックのほうが単価が安い**
- まとめ買いした食材は**一定期間で使い切らないと傷む**

を扱う必要がある。しかし ADR-003「レシピ情報を持たない」により、
`data/dishes.json` は料理名とタグしか持っておらず、材料も分量も一切ない。
材料データなしでは買い物リストも使い切り計算も作れない。

## Decision

ADR-003 のうち「食材量を持たない」部分を撤回し、以下の2ファイルを追加する。
**調理手順は引き続き持たない**（ADR-003 の著作権回避の意図はここで守られる）。

- `data/ingredients.json` — 食材マスター。購入単位（`packs`）・日持ち（`shelfLifeDays`）・
  冷凍可否（`freezable`）・常備品か（`pantry`）を持つ
- `data/dish-ingredients.json` — 料理ID → 材料と分量（2人分）

`packs` を「サイズと価格の配列」にしたのが要点で、これ1つで
「1本ずつは買えない」と「大容量のほうが安い」の両方を表現できる。
必要量に対して合計金額が最小になるパックの組み合わせを選ぶ。

材料データは**手で書く**。`scripts/tag-assign.ts` のようなキーワード推定では
分量の精度が出ず、買い物リストの金額がそのまま狂うため。

## Alternatives

- **料理名から材料を推定する**: タグ付けと同じ手法。分量が出せず却下
- **外部レシピAPIを使う**: ADR-005（DBなし・サーバーなし）と両立しない。
  静的エクスポートなのでビルド時取得しかできず、ライセンスの問題も残る
- **全224件に材料を付ける**: 品質を保てないので、まず主菜54件に絞る。
  材料データを持つ料理だけが献立プランナーの候補になる設計にして、後から増やせるようにした

## Consequences

- **メリット:** 買い物リスト・概算金額・使い切り警告が出せる。データを足せば候補が自然に増える
- **デメリット:**
  - 材料データが手作業なので、料理を増やすコストが高い
  - 価格が固定値。実売価格とはずれるので「目安」としてしか出せない
  - 献立プランナーの候補が54件しかなく、7日分だと選択肢が限られる
  - `data/dishes.json`（スクリプト生成）と `data/dish-ingredients.json`（手書き）で
    更新方法が違う。`tag-assign` が後者を壊さないよう、ファイルを分けてある
- 影響タスク: TASK-014
